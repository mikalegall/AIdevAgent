import { chromium } from 'playwright';
import { getBodyHTML } from './dom-snippets';
import * as fs from 'fs';
import * as path from 'path';

async function checkUI() {
  // 1. Käynnistys
  const browser = await chromium.launch();
  const page = await browser.newPage();
  const consoleErrors: string[] = [];

  // 2. Virheiden seuranta
  page.on('console', (msg) => {
    if (msg.type() === 'error') consoleErrors.push(`[CONSOLE]: ${msg.text()}`);
  });
  page.on('pageerror', (err) => consoleErrors.push(`[RUNTIME]: ${err.message}`));

  try {
    // 3. Navigointi (käytetään host-osoitetta kontin sisältä)
    await page.goto('http://host.containers.internal:5173', { 
      waitUntil: 'networkidle',
      timeout: 8000 
    });

    // 4. Otetaan kuvakaappaus (Aiderin visuaalista analyysia varten)
    const screenshotPath = 'ui-screenshot.png';
    await page.screenshot({ path: screenshotPath, fullPage: true });

    // 5. Haetaan DOM-rakenne
    const bodyHTML = await page.evaluate(getBodyHTML);
    const title = await page.title();

    // 6. Luodaan raportti
    const report = [
      `TIMESTAMP: ${new Date().toISOString()}`,
      `PAGE TITLE: ${title}`,
      `SCREENSHOT SAVED TO: ${screenshotPath}`,
      "\n--- CONSOLE ERRORS ---",
      consoleErrors.length > 0 ? consoleErrors.join('\n') : "No errors.",
      "\n--- DOM STRUCTURE ---",
      bodyHTML.substring(0, 5000), // Rajoitetaan pituutta, ettei konteksti täyty
      "\n--- END ---"
    ].join('\n');

    fs.writeFileSync('ui-status.txt', report);
    console.log('UI check complete. Report and screenshot generated.');

  } catch (error: any) {
    fs.writeFileSync('ui-status.txt', `CONNECTION FAILED: ${error.message}`);
  } finally {
    await browser.close();
  }
}

checkUI();

# Project Instructions: React Architecture

## Core Tech Stack
- **Framework:** React + TypeScript (Vite)
- **Styling:** Styled Components (Prefix: `Styled[ComponentName]`)
- **UI/A11y:** React Aria Components
- **State:** RTK Query (Server) & Redux Toolkit Slice (UI)
- **Icons:** Use the `material-symbols` npm package. 

## Architecture & Coding Rules
1. **Colocation:** Every component must have its own folder in `src/components/` containing the `.tsx`, `.styled.ts`, and `index.ts`.
2. **Strict TS:** No `any`. Use proper interfaces/types.
3. **API:** Use the Axios-based `baseQuery` in RTK Query.
4. **Clean Code:** Use arrow functions and descriptive naming.
5. **Icons Handling:** - Icons are used via the `<Icon>` styled component located in `src/components/Icon/`.
   - Icon names follow the Material Symbols Outlined naming convention.
   - Do NOT add CDN links to `index.html`.

### API-Driven Development Rules
1. **API Contract First:** Always refer to the `api-spec.md` (or Swagger/OpenAPI file) before creating components or RTK Query slices.
2. **Type Safety:** Generate TypeScript interfaces directly from the API definitions. Do not guess property names.
3. **RTK Query Mapping:** - Each API resource should have its own service file in `src/features/[resource]/[resource]Api.ts`.
   - Use `transformResponse` if the API data structure needs to be flattened or modified for the UI.
4. **Mocking (MSW):** If the Backend is not yet available, use Mock Service Worker (MSW) to simulate API responses based on the spec.

## Debugging Protocol
- If a component fails to render, provide a detailed explanation of potential causes.
- If I provide a console error, treat it as a high-priority task.
- Ensure that all API calls have proper `error` state handling (RTK Query), so that error messages are visible in the UI instead of silently failing.

## TDD Workflow (Mandatory)
1. **Test First:** Before writing any component logic, create a test file in the component folder (e.g., `MyComponent.test.ts` or `MyComponent.spec.ts`).
2. **Failure:** Run the tests and confirm they fail.
3. **Implementation:** Write the minimal code to pass the test.
4. **Visual Check:** Use Playwright for UI-heavy components to ensure correct DOM structure and accessibility.
5. **Report:** If a test fails, read the test output/report file and fix the code immediately.

## Frontend Secure Coding Rules (Mandatory for AI Dev Agent)
These rules apply to **all React components, hooks, state logic, and API integrations**.

### 1. Rendering & XSS Prevention (OWASP A03, CWE-79)
- React escaping is relied upon by default.
- All rendering must be **declarative and safe by construction**.

Forbidden:
- `dangerouslySetInnerHTML`
- Manual DOM manipulation
- Rendering raw HTML from API responses
- Using `eval`, `new Function`, or similar

Required:
- JSX rendering only
- Explicit sanitization if HTML rendering is unavoidable (must be justified)

### 2. Trust Boundaries (OWASP A04, CWE-20)
- Backend responses are **untrusted input**.
- API data MUST be treated as potentially malformed.

Forbidden:
- Assuming backend data shape without validation or mapping
- Blind spreading of API objects into components

Required:
- Explicit mapping of API → UI models
- Defensive rendering (null/undefined safe)

### 3. Authentication & Authorization Assumptions (OWASP A01)
- Frontend must NEVER enforce security decisions.
- UI checks are cosmetic only.

Forbidden:
- Relying on frontend logic for access control
- Hiding UI elements as a “security mechanism”

Required:
- Treat backend as sole authority
- UI reflects backend state only

### 4. Secrets & Configuration (OWASP A02, CWE-798)
- Frontend code is PUBLIC by default.

Forbidden:
- Secrets, tokens, API keys in frontend code
- Security-by-obscurity assumptions

Allowed:
- Public configuration values only
- Environment variables that are explicitly safe for client exposure

### 5. Dependencies & Supply Chain (OWASP A06)
- Frontend dependencies are a primary attack surface.

Forbidden:
- Adding dependencies for trivial helpers
- Copy-pasting code from unknown sources

Required:
- Prefer platform / framework features
- Every dependency must be justified in review

### 6. Error Handling & Logging (OWASP A09)
- Errors must be user-safe and developer-informative.

Forbidden:
- Exposing stack traces or internal details to users

Required:
- User-friendly error messages
- Debug information only in development mode

### 7. Explicit Rejection Rule
If a requested frontend implementation violates these rules, the AI Dev Agent MUST:
1. Stop
2. Explain which rule is violated
3. Propose a safe alternative

# Frontend architecture (reference)

Single source of truth for folder layout and imports. Keep this file updated when you add new top-level areas.

## Target `src/` layout

```text
src/
  app/                 # Router, app providers, error boundaries, layouts
  shared/
    ui/                # Shared primitives (Icon, layout helpers, …)
    lib/               # Pure helpers, formatters
  features/
    <feature>/
      components/      # Feature-specific UI (colocated folders per component)
      <feature>Api.ts  # RTK Query endpoints for this domain (naming may vary)
      model/           # Types and mappers (optional)
      slice.ts         # Redux slice if needed (optional)
  store/
    store.ts
    baseApi.ts         # RTK Query base + shared configuration
    …
  main.tsx
  index.css
```

## Import rules

1. **Features → shared, store, app** — Allowed.
2. **Feature A → Feature B internals** — **Not allowed.** Lift shared bits to `src/shared/` or expose a minimal public API in a dedicated shared module.
3. **Shared → features** — **Not allowed** (shared must stay generic).

## RTK Query

- `baseApi` (or equivalent) lives under `src/store/`.
- Feature-specific endpoints live under `src/features/<feature>/` and attach via `injectEndpoints` or the project’s agreed pattern—stay consistent with existing `store.ts` wiring.

## Related docs

- API contract: `docs/api-spec.md`
- Full agent rules: `.aider.instructions.md`

## Frontend Security Architecture

### Core Assumptions
- Frontend code is untrusted and public.
- Backend is the sole authority for security decisions.
- All external data is untrusted by default.

### Threat Model (Frontend)
- Cross-site scripting (XSS)
- Dependency and supply-chain attacks
- Unsafe rendering of dynamic data
- Accidental leakage of secrets
- Incorrect trust in backend responses

### Review Heuristics for Humans
When reviewing AI-authored frontend code, always check:
1. Is anything rendered as raw HTML?
2. Is backend data mapped defensively?
3. Are UI checks mistaken for security?
4. Does any dependency look unnecessary?
5. Could this leak information to the browser?
